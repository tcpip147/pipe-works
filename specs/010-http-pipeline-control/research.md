# 조사 기록: HTTP 파이프라인 제어

## 결정 1: 표준 라이브러리 기반 로컬 HTTP 서비스

- **결정**: 기존 의존성만으로 HTTP 요청 처리와 브라우저 화면을 제공한다.
- **근거**: 기능 범위는 소수의 로컬 운영자를 위한 목록·상태·시작·중지이며, 새 웹 프레임워크·빌드 체인 없이 실행 가능하다.
- **대안**: 별도 웹 프레임워크를 추가하는 방법. 향후 인증, 복잡한 화면, 원격 다중 사용자 지원이 필요할 때 재검토한다.

## 결정 2: 설정은 읽기 전용 등록원

- **결정**: 파이프라인 정의는 기존 `plumber.yml`과 개별 YAML에서 시작할 때 한 번 읽는다.
- **근거**: 기존 설정 계약을 유지하고, API가 영상 처리 설정을 임의로 바꾸는 위험을 피한다.
- **대안**: API에서 등록·수정·삭제를 지원하는 방법. 설정 검증, 저장, 동시성 정책이 추가로 필요하므로 이번 범위에서 제외한다.

## 결정 3: 상태는 프로세스 생명 주기에서 계산

- **결정**: 별도 상태 저장소 없이 보유 중인 자식 프로세스와 명시적 중지 이력을 사용해 상태를 산출한다.
- **근거**: 서비스 재시작 뒤 실행 단위가 유지되지 않는 현재 운영 모델과 맞고, 최소 감독 책임을 유지한다.
- **대안**: 상태와 작업 이력을 영속화하는 방법. 서비스 재시작 복구 요구가 생길 때 검토한다.
