# 기능 명세: 종단 간 비디오 파이프라인 계약

**기능 식별자**: `008-end-to-end-pipeline-contract`

## 기능 요구사항

- **FR-001**: 시스템은 RTSP 수신 → NVDEC → AI 추론 → NVENC → RTSP 송출 순서를 유지해야 한다.
- **FR-002**: 각 단계의 오류는 자체 복구, 원본 전달, 또는 상위 프로세스 실패 중 하나로 명확히 분류해야 한다.
- **FR-003**: GPU 프레임은 디코드부터 인코드까지 GPU 경로를 유지하고 송출 직전에만 CPU bytes로 변환해야 한다.
- **FR-004**: 큐 포화 시 최신 패킷 우선 정책을 적용하고 전체 파이프라인을 중단하지 않아야 한다.
- **FR-005**: 모든 단계는 연결 상태·처리 실패·재시작·종료를 식별 가능한 로그로 기록해야 한다.

## 성공 기준

- **SC-001**: 종단 간 모의 테스트에서 100개 프레임이 정의된 순서로 전달된다.
- **SC-002**: 단일 단계 장애가 정의된 복구 정책에 따라 처리된다.

## 구현 계약

- 수신 오류는 `receive.py`가 재연결하고, 송출 오류는 `send.py`가 컨테이너를 폐기한 뒤 재시도한다.
- 추론 오류는 `cli.py`가 로그를 남기고 원본 GPU 프레임을 인코더로 전달한다.
- 디코더·인코더 초기화 오류와 지원하지 않는 형식 오류는 상위 호출자에게 전파한다.
- 송출 heartbeat는 성공적인 `mux()` 이후에만 갱신된다.
- GPU 프레임은 decode·inference·encode 단계에서 유지되며, 인코더 패킷은 `cli.py`에서 CPU bytes로 변환된 후 송출 큐에 들어간다.
- 현재 프로젝트는 단계별 로그를 제공하며, 종단 간 단일 상관 ID는 사용하지 않는다.

## 현재 구현 기준

- 파이프라인당 하나의 CUDA stream을 생성해 NVDEC 생성자, `on_frame()` 실행 컨텍스트,
  NVENC 생성자에 공유한다.
- 입력 RTSP 패킷 및 송출 RTSP 패킷은 CPU 메모리에 존재한다. NVDEC 출력부터 NVENC 입력까지의
  프레임 픽셀 데이터는 DLPack을 통해 GPU 메모리에서 공유된다.
- 현재 출력 NVENC는 약 1초 IDR 주기를 목표로 한다. 실제 IDR 시각 및 수신자 측 첫
  디코딩 시각은 운영 로그와 WebRTC 수신 통계로 별도 관찰한다.
