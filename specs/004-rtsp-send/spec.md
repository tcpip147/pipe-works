# 기능 명세: RTSP 송출 및 Sender 감시

**기능 식별자**: `004-rtsp-send`  
**작성일**: 2026-09-14  
**상태**: 초안

## 개요

NVENC이 생성한 압축 패킷을 RTSP 출력 스트림으로 송출한다. 송출 작업은 별도 프로세스에서 수행하며, mux 성공 시 heartbeat를 갱신하고 송출 중단이나 장기 무응답을 자동 복구한다.

## 사용자 시나리오 및 검증

### 사용자 스토리 1 - 패킷 송출 (P1)

운영자는 인코딩 패킷을 설정된 RTSP 주소로 연속 송출받는다.

**검증**: 모의 컨테이너에서 패킷이 스트림에 연결되어 `mux`되는지 확인한다.

### 사용자 스토리 2 - 무응답 감시 및 재시작 (P1)

운영자는 mux가 10초 이상 성공하지 않으면 Sender 프로세스만 자동 재시작되기를 원한다.

**검증**: heartbeat 정지 또는 프로세스 종료 시 기존 프로세스가 정리되고 새 프로세스가 시작되는지 확인한다.

### 사용자 스토리 3 - 안전한 종료 (P1)

운영자는 종료 요청 시 감시 스레드와 Sender 프로세스가 제한 시간 내 종료되기를 원한다.

## 기능 요구사항

- **FR-001**: 시스템은 설정된 URL과 전송 방식으로 RTSP 컨테이너를 열고 출력 스트림을 구성해야 한다.
- **FR-002**: 시스템은 패킷의 코덱·해상도·시간 기준·PTS를 출력 스트림에 적용하고 mux해야 한다.
- **FR-003**: 시스템은 첫 mux 성공 이후에만 연결 성공 로그를 기록해야 한다.
- **FR-004**: 시스템은 mux가 성공할 때마다 heartbeat를 갱신해야 한다.
- **FR-005**: heartbeat가 10초 이상 갱신되지 않거나 Sender 프로세스가 종료되면 해당 프로세스만 재시작해야 한다.
- **FR-006**: 종료 시 감시 스레드와 Sender 프로세스를 graceful join 후 terminate/kill 순서로 정리해야 한다.
- **FR-007**: 큐가 가득 차면 최신 패킷을 우선하고 송출 전체를 중단하지 않아야 한다.
- **FR-008**: 별도 송신 워커 프로세스는 YAML의 파이프라인 이름으로 자체 로그 필터를 초기화하여, 송신 로그에도 해당 이름을 기록해야 한다.

## 성공 기준

- **SC-001**: 정상 mux 환경에서 패킷 100개가 누락 없이 순서대로 전달된다.
- **SC-002**: 10초 이상 heartbeat가 없을 때 감시 주기(최대 1초) 내에 1회 감지되고, 재시작 호출이 5초 이내 수행된다.
- **SC-003**: 종료 요청 후 `join` 제한 시간 1초, 강제 종료 단계별 제한 시간 2초를 합산한 5초 이내 감시 스레드와 자식 프로세스가 종료된다.

## 추가 운영 계약

- 큐 기본 크기는 30이며 `submit()`은 최대 1초 대기한다.
- 송출 오류 시 컨테이너와 스트림을 폐기하고 1초 후 재시도한다.
- 종료가 시작되면 감시 스레드는 자동 재시작을 수행하지 않는다.
- 재시작 횟수 제한이나 지수 backoff는 현재 제공하지 않으며, timeout 동안 무한 재시작할 수 있다.
- 종료 시 큐에 남은 패킷은 보존하지 않고 큐를 닫는다.

## 현재 구현 기준

- 구현 파일은 `src/nvidia_pipe/send.py`이다. 새 송출 연결 또는 송출 오류 뒤에는
  Annex-B H.264 IDR(NAL type 5) 및 H.265/HEVC IDR(NAL type 19, 20) 전까지 패킷을
  폐기한다.
- 큐 포화 시 가장 오래된 패킷 하나를 제거하고 새 패킷을 넣는다. 이 정책은 최신성은
  우선하지만 프레임 연속성을 보장하지 않는다.
- 송신 워커는 별도 spawn 프로세스이며, 첫 성공적인 `container.mux()` 뒤에만 연결
  성공 로그와 heartbeat 갱신을 수행한다.
