# 비디오 브로커 헌법

## 핵심 원칙

### I. 엔드투엔드 실시간 파이프라인

시스템은 RTSP 수신, NVDEC 디코드, AI 추론, NVENC 인코드, RTSP 송출의 순서를
보존하는 실시간 파이프라인으로 동작해야 한다. 각 단계는 지연 누적보다 최신 영상의
전달을 우선하며, 프레임 손실 정책은 명시적으로 정의해야 한다. 이 원칙은 감시 영상의
최신성과 운영 예측 가능성을 보장한다.

### II. GPU 경로와 자원 격리

디코드와 인코드는 가능한 한 GPU 메모리 경로를 유지해야 하며, 불필요한 CPU 복사와
프레임 변환을 추가해서는 안 된다. 각 파이프라인은 GPU 번호, CUDA 자원, 입력 및 출력
RTSP 주소를 명시적으로 설정해야 하며, 여러 파이프라인은 서로의 상태와 자원을
침범해서는 안 된다.

### III. 송출 복구와 정상성 기준

RTSP 송출의 정상성은 컨테이너 생성이 아니라 실제 `mux` 성공으로 판단해야 한다.
송출이 설정된 제한 시간 동안 성공하지 않으면 송출 담당 구성 요소만 우선 재연결하거나
재시작해야 한다. 재연결 이후에는 디코더가 복원할 수 있는 keyframe 전송을 보장해야
한다. 이 원칙은 GPU 파이프라인의 불필요한 재초기화를 피하면서 영상 복구를 보장한다.

### IV. 관측 가능하고 실패를 숨기지 않는 운영

수신 연결, 디코더와 인코더 초기화, 모델 추론, 송출 연결 및 재시작은 구조화된 로그로
기록해야 한다. 모델이나 CUDA 오류를 포함한 예외를 조용히 무시해서는 안 되며, 지속된
실패는 파이프라인 상태와 종료 코드에 반영해야 한다. 운영자는 로그만으로 어떤 단계가
정지하거나 재시작되었는지 확인할 수 있어야 한다.

### V. 단순한 감독 구조와 명확한 종료

plumber는 파이프라인 프로세스를 생성, 감시, 종료하는 감독자이며, nvidia_pipe는 단일
영상 파이프라인의 내부 생명주기를 소유한다. 종료 시 모든 하위 실행 단위는 제한된
시간 안에 정상 종료를 시도하고, 실패하면 강제 종료해야 한다. 플랫폼 전용 기능은
일반적인 Python 프로세스 관리로 해결할 수 없고 운영상 필요한 경우에만 도입한다.

## 추가 제약 조건

모든 명세, 계획, 작업 목록, 운영 문서 및 사용자 대면 로그 메시지는 한글로 작성해야
한다. 코드 식별자와 외부 라이브러리·프로토콜 이름은 기술적 정확성을 위해 영어를
사용할 수 있다. 설정 파일에는 입력과 출력 RTSP 주소, GPU 번호, 추론 모델, 프레임
처리 정책 및 상태 확인 제한 시간을 명시해야 한다.

## 개발 절차 및 품질 게이트

기능 변경은 수신·디코드·추론·인코드·송출·종료 중 영향 받는 단계를 명시한 명세에서
시작해야 한다. 구현 전에는 복구 정책, 리소스 소유자, 실패 시 동작을 설계해야 한다.
변경 후에는 최소한 구문 검사와 단위 검증을 수행하고, RTSP와 GPU가 필요한 변경은
실제 입력·출력 스트림을 사용한 통합 검증 결과를 기록해야 한다. 재연결, 프로세스
종료, 프레임 드롭, keyframe 복구를 바꾸는 변경은 회귀 검증 대상이다.

## 거버넌스

이 헌법은 프로젝트의 구현 관행과 개별 작업 지시보다 우선한다. 변경 제안은 영향을
받는 원칙, 호환성 영향, 필요한 이행 절차를 문서화해야 한다. 원칙을 제거하거나
의미를 재정의하면 주 버전을 올리고, 원칙 또는 의무를 추가하면 부 버전을 올리며,
의미를 바꾸지 않는 표현 정정은 패치 버전을 올린다. 모든 명세 검토와 코드 검토는
본 헌법 준수 여부를 확인해야 하며, 예외는 근거와 만료 조건을 문서화해야 한다.
